## Сценарии использования
### Сценарий 1. Создание заявки на бронирование
**Роль:** Клиент

**Предусловия:** 
- Пользователь авторизован
- В системе есть доступные для бронирования места

**Шаги:**
1. Пользователь настраивает фильтры для поиска доступных мест, выбирая дату и время начала и окончания бронирования
2. Сервис показывает доступные места с учетом выбранных фильтров и стоимость бронирования
3. Пользователь выбирает место и создает заявку на бронирование
4. Система проверяет, доступно ли еще выбранное место для бронирования, в случае если недоступно - сообщает об этом пользователю и предлагает выбрать другое место для брони, возвращая новый список с учетом выставленных пользователем фильтров, иначе - сценарий переходит к следующему шагу
5. Сервис перенаправляет пользователя на страницу оплаты бронирования и замораживает выбранное место на N минут
6. Пользователь в течение N минут оплачивает услугу, иначе заморозка выбранного места сбрасывается

**Результат:** Заявка на бронь места в коворкинге создана, забронированное место отображается в личном кабинете пользователя с указанием даты и времени действия брони.

**Граничный случай - двойная бронь:** Два пользователя A и B в двух параллельных сессиях выбирают пересекающиеся интервалы при выставлении фильтров для поиска мест для бронирования. При выборе пользователем A места система замораживает возможность повторного бронирования данного места на N минут до внесения оплаты пользователем A. В случае, если пользователь B выберет то же самое место, на шаге 4 система вынесет ему предупреждение о том, что данное место уже занято и необходимо выбрать другое. Таким образом, повторная бронь одного и того же места на пересекающийся период времени недоступна.

### Сценарий 2. Создание тарифа
**Роль:** Управляющий коворкингом

**Шаги:**
1. Пользователь открывает форму создания тарифного плана и указывает характеристики создаваемой сущности, например, наименование, начальную цену, единицу её измерения и период действия цены
2. Система проверяет валидность введенных данных и возвращает список ошибок, в случае их наличия, иначе - выводит пользователю окно с подтверждением создания тарифного плана
3. Пользователь подтверждает создание тарифного плана
4. Система сохраняет тарифный план и первоначальную стоимость тарифного плана, единицей измерения и периодом действия цены

**Результат:** Создан тарифный план, доступный для назначения местам и секциям коворкинга.

### Сценарий 3. Назначение тарифного плана местам или секциям коворкинга
**Роль:** Управляющий коворкингом

**Предусловия:**
1. Сконфигурирован тарифный план для оплаты бронирования
2. В систему загружена карта коворкинга с местами и секциями

**Шаги:**
1. Пользователь выбирает тарифный план
2. Пользователь выбирает одно или несколько мест либо секций, к которым необходимо применить выбранный тарифный план
3. Пользователь указывает дату и время начала и окончания действия тарифного плана
4. Система проверяет валидность введенных данных и возвращает список ошибок, в случае их наличия, иначе - выводит пользователю окно с подтверждением применения нового тарифного плана в выбранным объектам
5. Пользователь подтверждает применение нового тарифного плана к выбранным местам
6. Система сохраняет привязки тарифного плана к выбранным объектам, а также пользователя, внесшего изменения

**Результат:** Тарифный план назначен выбранным местам или секциям на указанный период.

**Граничный случай — пересечение действия тарифных планов:** в случае пересечения действия тарифных планов в части мест или секций пользователю открывается окно для редактирования, в котором доступно изменение действия нового тарифного плана для каждого из выбранных мест.

**Граничный случай — в системе присутствуют бронирования, созданные по старым ценам, на будущую дату, на которую должна действовать новая цена:** новая цена бронирования начинает действовать для бронирований, созданных после привязки тарифного плана к местам или секциям, старые бронирования стоимость не меняют.

### Сценарий 4. Регистрация прихода и ухода клиента

**Роль:** Сотрудник ресепшена

**Предусловия:**
- Сотрудник ресепшена авторизован
- У клиента есть действующее оплаченное бронирование

**Шаги:**
1. Сотрудник находит бронирование клиента
2. Система показывает сведения о бронировании и статус оплаты
3. Сотрудник подтверждает приход клиента
4. Система сохраняет дату и время прихода в бронировании
5. При уходе клиента сотрудник открывает бронирование и подтверждает уход
6. Система сохраняет дату и время ухода в бронировании

**Результат:** В бронировании сохранены дата и время прихода и ухода клиента.

**Граничный случай — повторная регистрация прихода:** если время прихода в бронировании уже заполнено, система показывает сохранённые данные и не изменяет время прихода.

**Граничный случай — уход клиента не зарегистрирован:** если клиент ушёл из коворкинга, но не зарегистрировал уход у сотрудника ресепшена, по истечении срока бронирования система автоматически заполняет дату и время ухода в бронировании датой и временем окончания его действия, только если приход зарегистрирован, а уход не зарегистрирован. Уже зарегистрированное время ухода не изменяется.

### Сценарий 5. Редактирование списка ролей пользователя

**Роль:** Администратор, пользователь, чей список ролей редактируется

**Предусловия:**
- Администратор авторизован 
- Учётная запись пользователя существует

**Шаги:**
1. Администратор находит учётную запись
2. Система показывает текущие роли пользователя
3. Администратор редактирует список текущей ролей пользователя
4. Система сохраняет назначение и применяет соответствующие права доступа

**Результат:** 
- в случае добавления роли пользователь получает доступ к действиям и данным назначенной роли
- в случае удаления роли пользователь теряет доступ к действиям и данным удаленной роли

**Граничный случай - повторное назначение роли:** при попытке повторно назначить ту же самую роль пользователю система возвращает ошибку.

## Связи и кардинальности
Сущности "пользователи" и "роли" связаны с помощью сущности "роли пользователей" отношением M:N - у одного пользователя может быть от нуля до нескольких ролей и роль может одновременно принадлежать нескольким пользователям. Пользователь может существовать без назначенных ролей, роль в свою очередь может существовать без привязки к пользователю.

Сущности "пользователи" и "места коворкинга" связаны с помощью сущности "бронирования" отношением M:N - один пользователь может забронировать несколько мест в коворкинге и одно и то же место в коворкинге может быть забронировано разными пользователями. В то же время сущности "пользователь" и "бронь" связаны отношением 1:N - пользователь может одновременно забронировать несколько мест в коворкинге, но бронь может принадлежать только одному пользователю. Аналогично сущность "место в коворкинге" связано с "бронью" отношением 1:N. Пользователь может существовать без создания бронирования, как и место в коворкинге может существовать без наличия брони на это место, однако бронирование не может существовать без пользоватля, либо без места в коворкинге.

Сущности "пользователи" и "платежи" связаны отношением 1:N - пользователь может сделать несколько платежей, но платеж всегда принадлежит одному пользователю. Пользователь может существовать без внесенного платежа, но платеж всегда требует существования пользователя.

Сущности "тарифный план" и "места в коворкинге", также как и "тарифный план" и "секции коворкинга" связаны отношением 1:N с помощью сущностей "Назначения тарифов местам" и "Назначения тарифов секциям" - один тарифный план может применяться к нескольким местам/секциям в коворкинге и в разные промежутки времени на одних и тех же местах/секциях в коворкинге действуют разные тарифные планы. В то же время отношения сущностей "тарифный план" <-> "Назначения тарифов местам", "тарифный план" <-> "Назначения тарифов секциям", "места в коворкинге" <-> "Назначения тарифов местам" и "секции коворкинга" <-> "Назначения тарифов секциям" связаны отношением 1:N. Тарифный план может существовать без собтвенной привязке к месту или секции в коворкинге, однако назначение без тарифного плана, секции в коворкинге, либо места в коворкинге существовать не может. Место в коворкинге требует существование секции, наоборот - нет.

Сущности «тарифный план» и «источрия изменения цен тарифных планов» связаны отношением 1:N. Тарифный план может существовать без цены, но бронирование нельзя создать на место, к которому прикреплен тарифный план без цены.

Сущности «Пользователи» и «История изменения цен тарифных планов» связаны отношением 1:N: пользователь может внести несколько записей о ценах или ни одной, каждая запись обязательно относится к одному пользователю, внёсшему цену (assigned_by).

## Бизнес-правила и ограничения
1. Стоимость тарифного плана не может быть отрицательной
2. Одновременно для одного тарифного плана не может действовать более 1 цены.
3. Изменение цены тарифного плана не влияет на стоимость бронирований, созданных до ее изменения
4. Не может существовать два и более тарифных плана с одинаковым названием
5. Не может существовать два назначения тарифного плана секции или месту в коворкинге с пересекающимся периодом действия; однако может присутствовать пересечение периода действия тарифного плана А места в коворкинге с тарифным планом B секции, которой принадлежит данное место - в таком случае приоритетным является тарифный план места в коворкинге
6. Не может существовать два пересекающихся бронирования одного и того же места в коворкинге
7. Не может существовать два места в коворкинге в пределах одной секции с одинаковым названием
8. У пользователя должны быть заданы контактные данные: либо номер телефона, либоб email, либо оба
9. Одну и ту же роль нельзя повторно назначить одному и тому же пользователю; сочетание ID роли и ID получателя уникально.

## Профиль нагрузки
- работа с бронированием, оплатой является нагрузкой с типом OLTP - короткие транзакции
- работа с построением отчетности по посещаемости коворкинга, платежами за бронирование относится к нагрузке с типом OLAP - построение отчетов/агрегатов

Ожидаемые объемы данных:
- пользователи: сотни
- роли: десятки
- роли пользователей: тысячи
- места в ковркинге, секции в коворкинге: сотни
- бронирования, платежи: тысячи
- тарифные планы: сотни
- история изменения цен тарифных планов: тысячи
- назначения тарифных планов: тысячи

## Нефункциональные требования
- Доступность
  - сервис должен быть доступен пользователем круглосуточно (коворкинг круглосуточный), 7 дней в неделю
  - доступность системы должна составлять не менее 99.5% за месяц, то есть для месяца суммарное время недоступности не должно превышать 3 часов 36 минут
- RPO - 15 минут; RTO - 1 час
- Безопасность
  - клиенту доступна информация только собственной учетной записи, а также история собственных бронирований и оплат
  - клиент может просматривать занятость мест на выбранный период времени без доступа к персональным данным клиентов, осуществивших бронирование
  - сотруднику ресепшена доступны ФИО и контактные данные клиентов, а также подробная информация об их бронированиях, времени прихода и ухода и истории оплаты
  - администратору доступны данные учётных записей пользователей, необходимые для управления ролями и правами доступа
  - система должна проверять права доступа при каждом запросе
  - пароли не должны храниться в открытом или обратимо зашифрованном виде
  - пароли и их хеши не должны отображаться пользователям, сотрудникам и администраторам через интерфейс или API системы
  - пользователь может изменить личный пароль после подтверждения владения учётной записью; администратор может инициировать сброс пароля пользователя; при сбросе пользователь задаёт новый пароль, прежний становится недействительным
